# Understanding the Vivado SRIO Gen2 IP

## 1. Background

When using the Vivado SRIO Gen2 IP, the part that users need to understand most is the User Interface. Once the data format and timing of the user interface are clear, high-speed data transfer can be implemented with the SRIO Gen2 IP without studying every low-level detail of the RapidIO protocol.

The User Interface of the SRIO Gen2 IP primarily consists of the I/O port and several optional ports. Common I/O transactions, including `NWRITE`, `NWRITE_R`, `SWRITE`, `NREAD`, `RESPONSE`, and `DOORBELL`, can all be transmitted or received through the I/O port.

The I/O port can be configured in either `Condensed I/O` or `Initiator/Target` mode. The `Initiator/Target` port type handles request and response transactions separately and therefore provides four AXI4-Stream channels for I/O transaction transfer. The `Initiator/Target` port structure is shown below.

<img src="./Images/IO_Port.png" alt="I/O port" width="400">

In `Initiator/Target` mode, the channels perform the following functions:

- Requests generated by the local device are transmitted through the `ireq` channel;
- Responses generated by the remote device are received through the `iresp` channel;
- Requests generated by the remote device are received through the `treq` channel;
- Responses generated by the local device are transmitted through the `tresp` channel.

## 2. I/O Port Data Format

The I/O port of the SRIO Gen2 IP supports two data formats:

- `HELLO` format;
- `SRIO Stream` format.

The HELLO packet is a compact packet format. It standardizes the packet-header fields, simplifies the control logic, and aligns the data with transfer boundaries, which makes data management easier.

When writing Verilog logic, the user only needs to send data to the AXI4-Stream interface of the SRIO IP core according to the timing requirements of the `HELLO` format. The SRIO IP core automatically converts the `HELLO` packet into a standard RapidIO physical-layer packet and adds the required control symbols, idle sequences, and other information during transmission.

The receive process is the reverse of the transmit process. After receiving a standard RapidIO physical-layer packet, the SRIO IP core parses it, converts it into a `HELLO` packet, and presents it on the user-side interface for subsequent logic to process.

As a result, when designing the Verilog logic for a transaction, the user only needs to understand the `HELLO` packet structure and interface timing instead of dealing extensively with the RapidIO protocol and RapidIO packet format. The `HELLO` format is therefore generally recommended.

![HELLO header](./Images/HELLO_Head.png)

As shown below, different I/O transactions use different packet-header formats.

<img src="./Images/HELLO_Detail_1.png" alt="HELLO format details 1" width="700">
<img src="./Images/HELLO_Detail_2.png" alt="HELLO format details 2" width="700">

If the amount of data in a request transaction exceeds 8 bytes, the data length must be adjusted to the nearest supported value.

The data lengths supported by the `HELLO` format for read and write transactions are:

- 8 Bytes;
- 16 Bytes;
- 32 Bytes;
- 64 Bytes;
- 96 Bytes, supported only for read transactions;
- 128 Bytes;
- 160 Bytes, supported only for read transactions;
- 192 Bytes, supported only for read transactions;
- 224 Bytes, supported only for read transactions;
- 256 Bytes.

The packet header of a `HELLO` transaction is transmitted during the first valid clock cycle on the user interface. If the transaction carries a data payload, the payload is transmitted continuously immediately after the header.

Note that the packet's `Source ID` and `Destination ID` are placed in the `tuser` signal and must be transferred together with the packet header in the first valid clock cycle. After the first valid cycle completes, the IP core ignores the contents of `tuser` in subsequent cycles.

## 3. IP Core Configuration

After opening the IP configuration interface, the main tabs that require attention are Basic and I/O. The settings on the other tabs can generally remain at their default values.

### 3.1 Basic Tab

![SRIO Gen2 Basic tab](./Images/SRIO_Gen2_Basic.png)

- `Mode`: Operating mode of the IP core; either `Basic` or `Advanced` can be selected.
- `Link Width`: Link width, selectable as 1, 2, or 4. A wider link provides higher data-transfer bandwidth.
- `Transfer Frequency`: Transfer frequency of each serial lane, selectable as 1.25, 2.5, 3.125, 5.0, or 6.25. A higher transfer frequency provides greater link bandwidth.
- `Reference Clock Frequency`: Reference-clock frequency, selectable as 125 MHz or 156.25 MHz. This parameter specifies the frequency of the external clock source, such as an oscillator or PLL device, applied to the dedicated reference-clock pins of the FPGA serial transceiver.
- `TX Buffer Depth`: Transmit-buffer depth, selectable as 8, 16, or 32. It specifies the maximum number of packets that can be buffered in the transmit buffer.
- `RX Buffer Depth`: Receive-buffer depth, selectable as 8, 16, or 32. It specifies the maximum number of packets that can be buffered in the receive buffer.
- `Component Device ID`: Initial value of the `Base Device ID CSR` register after reset.
- `Device ID Width`: Width of the Device ID. The transmitter and receiver must use the same Device ID width; otherwise, a packet may be parsed incorrectly because its header fields are shifted. Most systems use an 8-bit `Device ID`, while the RapidIO core also provides a 16-bit `Device ID` option.
- `Unified Clock`: Select this option when `log_clk` and `phy_clk` in the user design use the same clock. Doing so can reduce clock-domain-crossing latency and the associated resource usage.
- `Transmitter Controlled`: When selected, the RapidIO core first attempts to use transmitter-controlled flow control. If the receiver does not support it, the core automatically switches to receiver-controlled operation. Transmitter-controlled flow control uses receive-buffer status and watermark information to minimize retry conditions.
- `Receiver Controlled`: When selected, the RapidIO core can use only receiver-controlled flow control. In this mode, the transmitter sends transactions normally, while the receiver performs flow control through the Retry protocol.
- `Transceiver control and status ports`: Enables additional transceiver control and status ports. These ports correspond to transceiver ports with the same names in the GTX/GTH user guide for the target device and are useful when debugging the high-speed serial link.

### 3.2 I/O Tab

![SRIO Gen2 I/O tab](./Images/SRIO_Gen2_IO.png)

- `Port I/O Style`: I/O interface type, configurable as `Condensed I/O` or `Initiator/Target`. In `Condensed I/O` mode, receive and transmit operations share one set of AXI4-Stream channels. In `Initiator/Target` mode, request and response transactions use independent AXI4-Stream channels.
- `I/O Format`: I/O port data format, configurable as `HELLO` or `SRIO Stream`. The `HELLO` format is generally recommended because it reduces the complexity of user-side logic. `SRIO Stream` is suitable for applications that require more complete control over the packet format.
- `Messaging`: Selects the port type for message transactions. The available options are `Combined with IO` and `Separate Messaging Port`. `Combined with IO` means that message transactions and I/O write transactions use the same I/O port. `Separate Messaging Port` means that message transactions use a separate transfer port; after this option is selected, the IP core generates dedicated AXI4-Stream channels for message transactions.
- `Maintenance`: Selects the port type for maintenance transactions. The maintenance-port type is normally `AXI4-Lite`.

## 4. PMA Loopback Example

### 4.1 Configure the IP

Set the link width to 2, enable the additional transceiver control and status ports, and leave the remaining settings at their defaults.

![IP configuration](./Images/Setting_IP.png)

### 4.2 Connect the IP

According to the GTH user guide, the GTH transceiver supports the following operating modes:

- Normal operating mode;
- Near-end PCS loopback;
- Far-end PCS loopback;
- Near-end PMA loopback;
- Far-end PMA loopback.

![GTH loopback port](./Images/GTH_Loopback_Port.png)

The `sim_train_en` signal controls the simulation training process:

- During simulation, `sim_train_en` should be set to 1;
- During operation on actual hardware, `sim_train_en` should be set to 0.

In this example, `gt_loopback_in[5:0]` is configured as `6'b010010`, placing the GTH in near-end PMA loopback mode.

![IP connections](./Images/IP_Connection.png)
